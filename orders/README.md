# Orders: задания 1 и 2

Один Python-сервис, PostgreSQL из стенда, HTTP API склада, банка и шины.
Дополнительных брокеров и веб-фреймворков нет. В стенде работает один экземпляр
Orders: это позволяет обойтись без распределённых блокировок и lease.

## Как устроен код

| Модуль | Ответственность |
|---|---|
| `app.py` | Создание зависимостей, HTTP-сервера и двух фоновых потоков |
| `config.py` | Чтение `PORT`, `DATABASE_URL`, `PAYMENT_URL`, `INVENTORY_URL`, `EVENTS_URL` |
| `domain.py` | Типы, публичные статусы, проверка заказов и событий |
| `ports.py` | Интерфейсы хранилища и соседних сервисов |
| `service.py` | Оформление заказа и восстановление незаконченной работы |
| `repository.py` | Весь SQL, схема, транзакции, переиспользование соединений |
| `gateways.py` | HTTP-вызовы, таймауты и перевод ответа банка в понятный исход |
| `worker.py` | Периодический запуск восстановления и отправки outbox |
| `bonuses.py` | Приём подтверждения доставки и чтение баланса |
| `http_api.py` | Маршруты, JSON и HTTP-коды |

Бизнес-логика не зависит от SQL или `urllib`: она вызывает интерфейсы из
`ports.py`. В unit-тестах их заменяют простые подделки. Воркеры планируют работу,
но не содержат вторую копию платёжной логики.

## Жизнь заказа

```text
POST /orders
  → проверка запроса
  → INSERT orders(status=pending, stage=reserve), COMMIT
  → Inventory.reserve(order_id)
  → stage=pay, COMMIT
  → Payment.charge(Idempotency-Key=order_id)
      → подтверждена оплата: [status=paid + INSERT outbox], COMMIT
      → банк отказал: stage=release, COMMIT → Inventory.release → rejected
      → исход неизвестен / временная ошибка: pending, восстановление в фоне
```

Сумма — `Σ qty × price_cents`, деньги храним целыми копейками.
`stage` — внутренний указатель, какую работу продолжить; он не меняет контракт
`pending / paid / rejected`.

**Заказ записывается до любого внешнего эффекта.** Иначе процесс мог бы упасть
после списания, не оставив данных для восстановления. Теперь даже при потере
HTTP-ответа запись заказа и его идентификатор остаются в PostgreSQL.

Быстрый путь пытается завершить заказ сразу. Сетевые вызовы используют общий
дедлайн `time.monotonic() + 0.8`: таймаут каждого вызова ограничен оставшимся
временем. Если времени не осталось, отвечаем `201 pending`. Шина вообще не
вызывается из HTTP-обработчика. Оставшиеся 0,2 секунды — запас для локальной
работы, а не гарантия при произвольной перегрузке или недоступности БД.

### Восстановление и оплата

Платёжный воркер каждые 0,2 секунды выбирает до 100 `pending`-заказов.
После получения права обработки он перечитывает заказ: другой поток мог уже
завершить его после первоначальной выборки.

- `reserve`: снова запрашиваем резерв с тем же `order_id`. Inventory возвращает
  существующий резерв, поэтому повтор безопасен. Затем сохраняем `pay`.
- `pay`: сначала спрашиваем `GET /payments?order_id=...`. Если списание найдено,
  фиксируем `paid`. Если нет, повторяем оплату с прежним ключом.
- `release`: повторяем снятие резерва. Лишь успешный `204` позволяет поставить
  `rejected`. Ошибка не теряет обязанность освободить товар.

Пустой lookup означает «списания не видно сейчас», а не «предыдущий запрос уже
закончился». Поэтому безопасность повторной оплаты обеспечивает постоянный
`Idempotency-Key=order_id`, включая повторы после перезапуска.

Исходы Payment различаются согласно контракту:

| Ответ | Решение |
|---|---|
| `200/201` | Оплата подтверждена |
| `402` | Банк отказал; начать освобождение резерва |
| `500` | Гарантированно не списано; допустим повтор |
| Таймаут, обрыв, неожиданный ответ | Неизвестно; проверять факт списания |

После явного `500` быстрый путь делает один короткий повтор. Остальные попытки
выполняет воркер. Существующий circuit breaker после трёх ошибок ограничивает
обращения к Payment, через пять секунд допускает пробу. Сохранена политика задания 1: успешный lookup закрывает breaker. Это признак
доступности API, а не доказательство списания; при пустом списке оплату всё равно
повторяем с тем же ключом. Ограничение этой простой политики: если lookup
работает, а только endpoint списания постоянно возвращает `500`, он не будет
защищён длительной паузой breaker; фоновые повторы ограничены циклом воркера.

### Почему два потока не обрабатывают один заказ

`OrderService` хранит набор активных `order_id`. Короткий `threading.Lock`
защищает только добавление и удаление идентификатора. HTTP-путь занимает свой
идентификатор **до INSERT**, воркер пропускает занятые заказы. `finally` снимает
отметку при завершении и исключении. SQL и HTTP выполняются без глобального
мьютекса, поэтому разные заказы не блокируют друг друга.

Набор не является хранилищем работы: после падения он исчезает, а этапы в БД
остаются. Для нескольких процессов такая защита недостаточна; в рамках задания
они не требуются.

## Исходящие события: transactional outbox

Проблема двух отдельных действий: сначала сохранить `paid`, потом отправить
событие. Между ними процесс может упасть. Отправка перед записью тоже неверна:
другие сервисы увидят оплату, которую Orders ещё не зафиксировал.

Поэтому `mark_paid()` выполняет в одной транзакции:

```sql
BEGIN;
UPDATE orders SET status = 'paid' WHERE ... RETURNING id;
INSERT INTO outbox (id, order_id) VALUES (...)
ON CONFLICT (order_id) DO NOTHING;
COMMIT;
```

В коде границы задаёт `with conn.transaction()`. Это важно: соединения созданы
с `autocommit=True`, а две обычные команды без явной транзакции фиксировались бы
независимо. При ошибке INSERT откатывается и UPDATE. Нельзя создать событие для
отсутствующего или отклонённого заказа.

Идентификатор события — `order.paid:<order_id>`. Время события хранится в outbox,
поэтому при повторах постоянны и `id`, и содержимое. Уникальный `order_id` не даёт
создать второе логическое событие при повторном подтверждении оплаты.

Отдельный outbox-поток выбирает до 100 неотправленных записей и публикует их.
После `202` записывает `sent_at`. При сетевой ошибке, другом HTTP-коде или ошибке
записи отметки прекращает пачку и повторяет через секунду. Таймаут — 0,5 секунды:
зависшая шина не занимает обработчики заказов или платёжный воркер.

Гарантия — доставка **как минимум один раз**, а не один HTTP-запрос.
Если шина приняла событие, а процесс упал до записи `sent_at`, публикация
повторится. Подписчик должен узнавать дубль по тому же `id`.

## Входящие события: журнал бонусов

`POST /webhooks/delivery` принимает `delivery.confirmed`. Поля `id` и `user_id`
непустые, `bonus_points` — положительное целое число, не `bool`. Событие не
обязано ссылаться на существующий заказ: бонусы принадлежат покупателю из события.

Вместо отдельной таблицы «обработано» и отдельного изменяемого баланса хранится
сам журнал начислений:

```sql
INSERT INTO bonus_deliveries (event_id, user_id, bonus_points)
VALUES (...)
ON CONFLICT (event_id) DO NOTHING;
```

`event_id` — первичный ключ. При одновременных дублях PostgreSQL согласует
конкурирующие вставки: остаётся одна запись. Одно выражение в autocommit — одна
атомарная операция: нет промежутка «пометили обработанным, но не начислили».

Ответ `200` отправляется после успешного завершения INSERT, в том числе для
дубля. Если запись не удалось подтвердить, возвращается `503`: шина повторит
доставку. Это поведение вебхука; ошибки соседних сервисов при оформлении заказа
не должны превращаться в `5xx` на `POST /orders`.

Баланс `GET /users/{id}/bonus` — `COALESCE(SUM(bonus_points), 0)` по покупателю.
Индекс по `user_id` помогает выборке. Параллельные разные события не теряют
прибавления: каждое создаёт самостоятельную строку.

## Что произойдёт при падении

| Момент остановки | Восстановление |
|---|---|
| До сохранения заказа | Внешние действия ещё не начинались |
| После резерва, до сохранения этапа | Идемпотентный повтор резервирования |
| После списания, до `paid` | Есть `pending`; lookup и прежний платёжный ключ |
| Во время транзакции `paid + outbox` | PostgreSQL фиксирует оба изменения или ни одного |
| После commit, до публикации | Запись outbox ждёт отправки |
| После публикации, до `sent_at` | Повтор того же события |
| После `402`, до снятия резерва | Сохранённый `release` продолжает компенсацию |
| Во время записи начисления | Незавершённая транзакция откатывается, шина повторяет |
| После начисления, до HTTP-ответа | Повтор упирается в первичный ключ, баланс прежний |

## Схема и ограничения

При старте создаются недостающие таблицы и колонка `stage`. Старые заказы
сохраняются; для старых `paid` добавляется отсутствующее событие outbox.
Миграция повторяема и не сбрасывает `sent_at`. В каждом сценарном прогоне стенд
создаёт пустую БД; при перезапуске только Orders база сохраняется.

Outbox и журнал бонусов растут. В учебном решении записи не удаляются.
В эксплуатации отправленные outbox-записи можно архивировать с учётом того,
что стартовая сверка не должна создать их заново. Журнал начислений хранит и
баланс, и защиту от повторов: удаление старых строк одновременно уменьшит баланс
и позволит повторное начисление. Для очистки потребуются архив/агрегаты и
договорённость о максимальном сроке повторной доставки. Произвольный TTL здесь
нарушил бы гарантии.

Переиспользование соединений осталось прежним: `max_size` ограничивает очередь
свободных соединений, а не общее число открытых. Сбой PostgreSQL не маскируется
фиктивным успешным оформлением: до надёжного сохранения нельзя обещать `201`.
Стенд проверяет отказы соседей и процесса Orders, а не отказ самой БД.

## Запуск и тесты

Из корня:

```bash
make scenarios TASK=1
make scenarios TASK=2
# Все S7/S8 запускаются через make: им нужен перезапуск Orders.
```

Быстрые тесты из `orders/`:

```bash
python3 -m unittest discover -s tests -v
```

Тесты PostgreSQL требуют отдельной **одноразовой** базы: они очищают таблицы.
Не указывать в `TEST_DATABASE_URL` рабочую базу `orders`.

```bash
# При уже поднятом стенде, из корня:
docker compose exec -T postgres psql -U orders -d postgres -c 'CREATE DATABASE orders_test'
docker compose run --rm --no-deps -T -v "$PWD/orders:/app:ro" \
  -e TEST_DATABASE_URL=postgres://orders:orders@postgres:5432/orders_test \
  orders python -m unittest discover -s tests -v
```

Без `TEST_DATABASE_URL` проверки PostgreSQL явно пропускаются. Они проверяют
откат `paid` при отказе outbox, конкурентные дубли начислений, восстановление
после незавершённой транзакции и обновление старой схемы.

## Вопросы для защиты

1. **Когда заказ оплачен?** Деньги фактически списывает Payment; Orders
   подтверждает это ответом или lookup, затем атомарно сохраняет `paid` и outbox.
2. **Почему не отправлять событие сразу?** Доступность шины увеличит время
   ответа, а падение между записью и отправкой потеряет уведомление.
3. **Почему возможны дубли?** Между принятием события шиной и отметкой в нашей
   БД нет общей транзакции. Повтор с прежним идентификатором безопасен для
   идемпотентного подписчика.
4. **Почему таймаут не означает отказ банка?** Ограничено наше ожидание,
   внешняя операция могла продолжиться. Поэтому нужны lookup и ключ операции.
5. **Почему бонусы не удвоятся при гонке?** Уникальность обеспечивает БД,
   а начисление совпадает с самой вставкой. Проверка наличия отдельным SELECT
   перед INSERT не нужна и сама по себе не защитила бы от гонки.
6. **Зачем этап `release`?** Сохранить обязанность снять резерв после отказа
   банка даже при остановке процесса или ошибке склада.
7. **Что хранится в памяти?** Только временная координация потоков и circuit
   breaker. Заказы, события и начисления переживают рестарт в PostgreSQL.
8. **Это exactly-once?** Доставка событий — at-least-once. Для бонусов достигаем
   однократного бизнес-эффекта с помощью уникального идентификатора в БД.
